# ADR-0008：实时推送用 SSE（服务端短轮询）

- 状态：已接受
- 日期：2026-09
- 决策者：sqhc

## 背景

Feed 之前靠前端轮询（打开页面取一次，翻页再取），"新内容出现"这件事对用户不可见。需要一个服务端 → 浏览器方向的推送。

## 决策

1. **用 SSE（`text/event-stream`）而不是 WebSocket**：只需要服务端单向推、天然支持断线重连（浏览器 `EventSource` 自带），
   且可以复用同一套 HTTP 鉴权/反代配置。
2. **服务端是"短轮询 + 推送"**（`app/api/v1/stream.py`，间隔 3 秒），而不是 Postgres LISTEN/NOTIFY：
   - 不需要数据库触发器与额外长连接，测试与本地开发都能直接跑；
   - 延迟上限 = 轮询间隔；多副本时每个副本各自轮询，客户端只连一个副本，语义正确。
   - 数据量上来后可换成 LISTEN/NOTIFY（或用 `pg_notify` 在写入时触发），**对外协议不变**。
3. **协议**：连接后先发 `event: ready`（带当前游标与轮询间隔），之后每条新富化文档一个 `event: document`（JSON 负载与 Feed 的 DocumentOut 字段对齐），
   空闲 15 秒发一次 `: ping` 心跳注释帧防止中间层断连。
4. **前端**：`useDocumentStream` 只做"收到就累加计数 + 5 秒内合并成一次刷新"，不直接改缓存——避免一次入库风暴打爆接口。
5. **不做历史补推**：默认从"当前最新一条之后"开始，历史走 Feed 的游标分页；需要续传可用 `?since=<id>`。

## 后果

- 每个打开的页面会每 3 秒查一次数据库。单机几十个连接没问题；规模上去要么拉长间隔，要么换成 NOTIFY。
- 断线后浏览器自动重连，重连会从"最新一条"开始，可能漏掉断线期间的条目——因此收到事件时前端是**刷新 Feed**，而不是插入单条，漏推不会造成数据缺失。

## 验证

`make smoke` 会拉起流并断言第一帧是 `ready`（`curl -N --max-time 4 /api/v1/stream | head -3`）。
