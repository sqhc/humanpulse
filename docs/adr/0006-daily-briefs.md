# ADR-0006：简报的生成方式（结构化 JSON + 服务端渲染）

- 状态：已接受（日报与周报均已实现）
- 日期：2026-09
- 决策者：sqhc

## 背景

平台的价值主张是"每天/每周用几分钟读完这段时期值得记录的事"。Feed 只能一条条看，需要聚合产物：日报与周报。
难点在于：既要**双语**，又要**可复现**、**不编造链接**，还要能在不额外花钱的前提下换语言重看。

## 决策

1. **模型只输出结构化 JSON**（`BriefContent`：标题/概述/分组/要点，中英各一份），**Markdown 由我们自己渲染**（`app/briefs/render.py`）。
   - 好处：同一份内容可以零成本重渲染成中/英 Markdown；渲染结果可测试；来源清单由我们按素材拼，模型没有机会编造链接。
   - 代价：提示词更长（要解释字段结构），且模型输出需要一次 Pydantic 校验。
2. **素材 = 按 cluster 去重后的 Top N**：同一事件只留评分最高的一条代表，避免头条被同一事件刷屏。日报 12 条、周报 20 条。
3. **幂等**：日报同一天只生成一次，周报同一自然周只生成一次；`force=True` 用于重跑（运维命令与冒烟测试用）。
4. **没有素材也要留痕**：写一条 `reason=no_items` 的占位简报，而不是静默跳过——否则"今天没更新"和"任务挂了"无法区分。
5. **分段固定**：conflict / science / labor / other，与平台三个长期议题一致；没有素材的分组直接省略。
6. **入口**：`POST /api/v1/admin/jobs/brief/run`（管理员，`kind=daily|weekly`）、`make brief KIND=weekly`、
   以及 worker 到 `BRIEF_HOUR` 之后每 15 分钟探一次（周报只在 `BRIEF_WEEKDAY` 当天）。生成函数幂等，所以探多次是安全的。

## 数据

- `briefs`：`kind(daily|weekly)`、`period_start/end`、`language`、`title`、`markdown`（zh 版，便于直接读）、`structured`（完整双语 JSON）、`model`、`prompt_version`、`cost_usd`。
- `brief_items`：`rank` + `document_id` + `cluster_id`，保留"这一期用了哪些素材"，便于回溯与重渲染来源清单。
- 迁移：`d86d2e05f291_phase_2_briefs`（up/down 均已验证）。

## 周报的差异（趋势数字由 SQL 算好）

1. **窗口 7 天**（`WEEKLY_LOOKBACK_DAYS`），素材上限 20 条，仍然按 cluster 去重。
2. **趋势统计在 `app/briefs/weekly.py` 用 SQL 算**：话题频次（`unnest(tags)` 分组计数）与**上周对比**、地区分布、
   本周新增 cluster 数、多来源 cluster 及其关键词、语言分布、仅标题素材占比。
   提示词明确要求"趋势里每条都要引用给定统计数字"——不让模型自己数数。
3. **输出多两个字段**：`trends_zh` / `trends_en`（各 3–6 条），渲染成 `## 本周趋势` / `## Trends`；日报留空时该段不出现。

## 后果

- 简报质量上限取决于选材：目前按评分排序，没有"与上一期相比的新颖度"衰减；周报趋势也只覆盖话题/地区/聚类。
- 素材摘要已经是双语，所以简报的双语不需要额外翻译调用（一次调用同时产出中英）。
- 若模型返回的 JSON 无法通过校验，`complete_json` 会带着错误摘要重试一次；两次都失败则整批抛出，已有数据不受影响。
- 实测（真实数据、deepseek-v4-pro）：周报一次调用约 6.5k 输入 / 8.7k 输出 token，耗时约 100 秒。

## 待办

1. 趋势里加入**实体共现**与**来源多样性变化**；
2. 用 cluster 的 `first_seen_at` 做新颖度排序，让"本周才出现的事"排在"持续发酵的事"前面；
3. 简报与上一期的差异对比（"本周 86 次 / 上周 4 次"已能做，"哪些话题消失了"还没做）。
