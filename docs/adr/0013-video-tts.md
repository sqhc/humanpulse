# ADR-0013：视频简报配音（TTS）与画面节奏

- 状态：已接受
- 日期：2026-10
- 决策者：sqhc

## 背景

ADR-0010 交付了无声字幕视频，并明确把 TTS 列为待办。这次补上配音——
但接上之后立刻暴露出**三个画面节奏上的问题**，它们在没有配音时同样存在，只是不容易发现。

## 决策

### 1. TTS 做成可插拔提供方，而不是绑定某个命令

- `macos-say`：本机开发用，`say -v Tingting`，零依赖、离线；
- `command`：模板接 `{text_file}` / `{out_file}`，可接 piper / edge-tts / 云 TTS；
- `none`：默认，产出无声字幕视频。

生产是 Linux 容器（没有 `say`），所以**默认值必须是 none**，不能假设本机能力。
文本走**文件**而不是命令行参数：旁白里有引号、换行、全角标点，塞进 argv 很容易出错。

### 2. 用真实音频时长覆盖估算时长

`apply_audio_durations` 在合成后把每镜时长改写成实际音频长度，并**重新落盘脚本与 SRT**——
否则字幕与成片对不上。估算时长只在没有音频时使用。

### 3. 拆镜，而不是压缩时长（修掉一个真 bug）

`scene_seconds` 原本把单镜时长夹在 `[2.5, 22]` 秒。真实数据里出现过一个 597 字的段落：
22 秒上限把它压成 8 秒画面——**观众根本读不完；配音版更是直接对不上**。

改为：不设上限，超过 soft 上限（24 秒）就按句拆成多张卡（`split_long_text`），
续卡标题带「（续）」。宁可多一次转场，也不要一张读不完的卡。

### 4. 「看的内容」与「念的内容」分开（`Scene.display`）

来源清单原本把「来源：英文标题」逐条念出来：中文语音读英文会明显加速，
实测该段 **8-12 字/秒**（正常是 4.8），听感像快进。

现在 `Scene.display` 与 `narration` 分离：屏幕列全量（供核对），语音只报
「本期素材共 20 条，来自 8 个来源：……」——同一批数据从 708 字降到 98 字。

## 实测数据（brief 3 周报，28 分镜）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 分镜数 | 14（1 张卡 597 字） | 28（每张 ≤24 秒） |
| 最短卡 | 1 个「。」 | 无低于 8 字的碎片 |
| 朗读速度区间 | 1.9 - 12.4 字/秒 | **4.24 - 5.91 字/秒** |
| 音画时长 | — | 视频 585.12s / 音频 585.24s（对齐） |
| 总时长 | 估算 272s（严重低估） | 估算 590s ≈ 实际 585s |

朗读速度常数 `CHARS_PER_SECOND['zh']` 先后写死过 5.5、6.2，都偏乐观；
按实测校准到 **4.8**（say Tingting @ rate 180）。不同语音节奏不同，它只是兜底估算。

## 后果

- 配音让脚本从「无声 PPT」变成可听的成片，但**画面仍是静态卡**（无动效、无配图）。
- 渲染耗时约等于视频时长的 1/10（28 镜约 50 秒），主要成本在逐镜编码。
- 生产要出配音必须自带 TTS：容器里没有 `say`；`TTS_PROVIDER=command` + piper 是成本最低的路径。
- 待办：每镜配图；多语音（中英双语各出一版）；字幕与配音的对齐校验（当前依赖时长覆盖）。
